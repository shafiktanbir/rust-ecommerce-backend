# V1 Architecture: The Monolith

## Overview

Version 1 is a single Rust process talking directly to PostgreSQL.

```
┌─────────────────────────────────────────────────────────┐
│                    CLIENT                               │
│  (curl, browser, k6 load tester)                        │
└────────────────────────┬────────────────────────────────┘
                         │ HTTP/1.1
                         ▼
┌─────────────────────────────────────────────────────────┐
│                 AXUM HTTP SERVER                        │
│                                                         │
│  Handler Layer                                          │
│    ↓  extract JSON, path params, query params           │
│  Service Layer                                          │
│    ↓  business rules, validation                        │
│  Repository Layer                                       │
│    ↓  SQL queries via sqlx                              │
│  Connection Pool (max 10 connections)                   │
└────────────────────────┬────────────────────────────────┘
                         │ TCP
                         ▼
┌─────────────────────────────────────────────────────────┐
│               POSTGRESQL 15                             │
│  (Docker container on localhost:5432)                   │
│                                                         │
│  Tables: users, products, orders, order_items,          │
│          flash_sales                                     │
└─────────────────────────────────────────────────────────┘
```

## Component Breakdown

### Tokio Runtime
- Multi-threaded: one OS thread per CPU core (default)
- Each thread runs an event loop
- When a handler awaits I/O (DB query), the thread switches to another task
- Result: thousands of concurrent requests on a handful of OS threads

### Axum Router
- Routes incoming HTTP requests to the appropriate handler function
- Extracts typed data (JSON bodies, path params, query params) via extractors
- Handlers are composed with Tower middleware layers (tracing, auth in future)

### Connection Pool (sqlx PgPool)
- Maintains a set of live PostgreSQL connections
- Requests borrow a connection from the pool, run their query, return it
- V1 pool size: **10 connections** (will measure and tune)
- If pool is exhausted, requests queue — this is the first bottleneck we'll observe

### PostgreSQL
- Single instance, running in Docker
- ACID transactions for safe inventory operations
- `inventory_count` column with `CHECK (inventory_count >= 0)` constraint

## V1 Concurrency Model

When 100 users simultaneously request `GET /products`:

1. Tokio accepts 100 concurrent TCP connections
2. Spawns 100 async tasks
3. Each task hits the DB pool
4. Pool has 10 connections → 90 tasks queue
5. As each of the 10 DB queries completes (~2–5ms), the connection is returned
6. Waiting tasks get connections in FIFO order
7. All 100 responses complete within ~50ms total

When 100 users simultaneously attempt to buy the last item (`POST /order`):

1. All 100 tasks hit the DB simultaneously
2. The `UPDATE products SET inventory_count = inventory_count - 1 WHERE inventory_count > 0` uses
   PostgreSQL row-level locking
3. Only one wins; the rest either block or fail gracefully
4. This lock contention is the first thing we will measure in the flash-sale scenario

## Known V1 Limitations (Future Bottlenecks)

| Limitation | Symptom | Future Fix |
|-----------|---------|------------|
| Single DB connection pool (10 connections) | p99 latency spikes under load | Increase pool size, measure PostgreSQL max_connections |
| No caching | Every request hits PostgreSQL, even for the same product | Redis in V2 |
| Single application process | One CPU core saturated → throughput caps | Load balancer + replicas in V3 |
| Synchronous order processing | Order request blocks until DB commits | Background queue in V4 |
| No read replicas | Write and read load compete on same DB | Read replicas in V5 |
| No circuit breaker | DB outage takes down the entire API | Resilience patterns in V9 |

## What V1 Will Teach Us

Before adding any complexity, we need baseline measurements:

```
Questions to answer after V1 load tests:
  - What is the maximum RPS the monolith can handle?
  - At what concurrency level does p95 latency exceed 200ms?
  - What is the CPU usage of the Rust process?
  - What is PostgreSQL CPU and connection count at peak load?
  - What breaks first — the app or the database?
```

The answers will determine which component we introduce in V2.
